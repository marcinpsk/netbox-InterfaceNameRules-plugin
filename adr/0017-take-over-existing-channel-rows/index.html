    Take over existing channel rows when building a channelized family

    When the plugin builds a channelized family on a plain port, a row that already has one of the planned channel names is taken over instead of counted as a collision, when it qualifies. Other tooling often creates the channel interfaces of a breakout optic on the device before the optic is modelled, with LAG membership, addresses and VLANs on them. Refusing the family because those rows exist left the device with flat rows and a parent that has no channels. This ADR revises ADR 0013 for channelized creation only: a channelized family can take a row by its name. A flat family still keeps only the rows the claim gives it, and a channelized family that the module already models still renames as before.

    A row with a planned channel name qualifies when it is not on another module (its module is empty or is the family's module), has no parent and no channel ID, and is not a channelized parent. A row with a cable does not qualify. A row that the claim (ADR 0013) gives a template does not qualify either, because another family is built on it: two ports whose families spell each other's names refuse both families, and each port keeps its own plan and its own report. NetBox 4.7 refuses a channel ID on an interface that has a cable termination, because a channel takes its cable from its parent. The plugin never edits or deletes a cable, so the operator must remove the cable first. One function, channel_holder_refusal, states this rule. Planning, the preview and execution all call it, so they cannot disagree about which rows qualify. Planning asks it on the rows it reads and refuses the family as a plan precondition; execution asks it again under lock. A channel name that the families on one module want more than once, inside one family or across two, is no family's to take over. Every family that wants it is refused, its reason names the row, and the row is reported once, by its own plan. This is decided once for the module, before any family runs, by repeated_names; planning, the preview and execution all use it, and execution asks it again under lock for its own plan. It replaces two failures. A family with a constant channel name bound one existing row as two channels, and two families that wanted one row both planned it, so the second one went stale and reported the row again. Refusing only the second family was rejected, because then the result depends on the order in which the families run. A family that wants a channel name no row has yet is refused the same way, where before the first family took the name and the second was refused. The parent name rule does not change: a row other than the base with the parent's target name refuses the family.

    To take over a row, the plugin keeps its primary key and name, and sets its module to the family's module, its parent to the family parent, its channel ID to the planned one and its type to channel. These are the values of a channel row that the plugin creates or that a conversion rewrites. Everything else on the row stays: LAG membership, addresses, VLANs, description, enabled state, tags and custom field values. NetBox's full_clean() validates each row that the family takes over, and a rejection names the row. A planned channel that has no row is created as before.

    The decision is all or nothing (ADR 0001). When one row with a planned name does not qualify, or NetBox rejects one row, the family is refused and no row changes. The reason names the row and says why it does not qualify. The refusal outcome reports the base and every row that the family would take over, once each, with that reason. A row that belongs to another module or to another family (its base, a subinterface or a channelized parent) is named in the reason but is not a member of the refusal: the outcome of its own module or family reports it, so a batch over several modules reports each row once. A row with no module is reported by no refusal either, only by the one family that takes it over, because families on several modules can want it and any of them could be refused. So a refusal reports the base and the rows of its own module, which no family on another module holds, and each interface is in at most one outcome of a batch. Choosing one refusing family to report such a row was rejected: the choice would depend on which modules the batch reads. A taken-over row is a member of the family outcome with status changed and the name it already had, so the Apply view counts it.

    A structural plan carries a snapshot of each row with a planned channel name. Execution runs in the family's own savepoint, inside the transaction of its module (ADR 0005). It locks the base and those rows in primary-key order and compares them with their snapshots (ADR 0002). A row that changed, that is gone, or that took a planned channel name after planning makes the plan stale. Discovering the rows only at execution was rejected, because then a row could change between the decision and the write with nothing to compare against.

    The preview asks the executor's question with the same function, so it offers a family whose rows all qualify and offers no family that the apply refuses. It records the reason that the apply gives. A channelized family always changes its base, so the preview offers it also when every name it needs exists already and the family only takes rows over. Prediction has no rows (ADR 0008), so it predicts the family whether or not a row with a channel name qualifies.

    A row that a family takes over is not a flat sibling. The check for an installed flat family (ADR 0010) counts the module's plain rows beyond its module type's templates. It is decided once for the module, over every family the run plans on it, and it leaves out each row with a channel name of one of those families, except a row the claim gives a template. A family that is refused for another reason, or that the operator's selection does not reach, takes over no row, so its rows still count. Otherwise the module's other families were built beside those rows, and the refused family could not be built later on that module. Deciding it per family was rejected, because then the rows that a second port takes over made a surplus for the first port, and two ports refused each other. Planning and the preview decide it the same way, and the preview checks it again after it refuses a family for a row it cannot take over. Each plan carries the names that the module's families take over, and execution leaves out the same names when it counts the module's rows under lock. The channelized families that one module builds run in one transaction. After the last of them, the transaction counts the module's plain rows again. When a row beyond the templates is left, a family that was refused at execution left it, or a concurrent write added it. Then every family built in that transaction rolls back and reports that a flat sibling would stay beside it. Without this, a family that failed validation or went stale at execution left its rows beside a family built before or after it. Planning the remaining families again after a refusal was rejected, because it does not undo a family that is already built. A flat apply gives the first row of a flat family a channel name, so this does not apply when the base itself has one of the planned channel names: then the rows are still that flat family, and only an operator-confirmed conversion changes them. For the same reason, under a channelized rule the claim (ADR 0013) does not read rows with the channel names as a flat family of a template while the module still has a port with that template's raw name. The claim recognises that port as it recognises any raw name (ADR 0013): the raw name now, a raw name the template gave earlier, or its raw name at an earlier virtual-chassis position that no other raw name holds, so a renumber that NetBox did not rename the port for does not change the decision. A flat apply renames the port, so rows beside a raw-named port came from other tooling. Without this, the claim found the port and those rows ambiguous and refused both. A row that the family takes over has no plan of its own, so it is reported once.
