    Run plugin writes and rename triggers on the write alias

    When netbox-branching is installed and a branch is active, its router sends every read and write of a branchable model to a second Django connection, the branch alias. netbox-branching writes a ChangeDiff row on default for each change in the branch. This ADR records how the plugin's writes and the rename-trigger lifecycle of ADR 0015 work on the write alias. It revises the connection and transaction decisions of ADR 0015. On main, with no branch or without netbox-branching, the behaviour does not change. The review history and the evidence are in docs/design/netbox-branching.md.

    The rename trigger works on the connection of the save. The receivers pass the signal's using, and raw stays unread. The trigger raises when using differs from the write alias that the router gives for Interface. It defers on the connection of using: it checks the atomic state of that connection, finds the plan in the commit callbacks of that connection, registers each trigger there with its savepoint tag, and appends the untagged runner there. The coalescing, the order and the savepoint filtering of ADR 0015 stay. In a branch, the plan runs after NetBox's branch transaction commits, so it runs after NetBox created the interfaces of a new module. The plan records its alias, and its runner opens the write scope with that alias as the expected alias. Event tracking is still active, so each rename gets an ObjectChange with its previous data in the branch. Checking the connection of default was rejected because in a branch default is not in an atomic block during a save, so the plan runs at once inside post_save, before the interfaces of a new module exist. Skipping raw saves was rejected because it changes behaviour on main, for example a fixture load of a module.

    Every plugin write runs inside a write scope, and the plugin writes only through an alias of the open scope. The scope pins the aliases of the operation: default on main, or default and the branch alias in a branch. With an expected alias, the scope raises before any query when the write alias differs. A nested scope inherits the outer one. A plugin transaction opens default as the outer block and the branch alias as the inner block. So the branch commits first and default second, as NetBox scripts and the netbox-branching sync nest them. Each member savepoint opens on both aliases, so a name collision rolls back that member on both connections and the other members continue. A rollback mark applies to every alias. The plugin keeps its queued events when the branch block commits, or is released when nested, with no alias marked for rollback. NetBox dispatches them only when its event context exits without an error. A transaction on the branch alias alone was rejected because a rollback then leaves ChangeDiff rows on default for changes that do not exist.

    In a branch only, the outermost scope sets a session-level lock_timeout of 10 seconds on both connections. A request in a branch holds two PostgreSQL sessions, and PostgreSQL does not detect a lock cycle through the two sessions of one request. It restores the previous value on each connection in a finally after the last commit callback of the plugin's own transactions. On main the scope runs no query. The timeout covers the plugin's own transactions and every callback that runs before the plugin's outermost scope exits. When a caller already holds a transaction on a connection, the scope sets and restores the timeout inside that transaction. PostgreSQL undoes a session SET when its transaction rolls back and keeps it when the transaction commits, so the connection keeps the value from before the transaction after either result. The callbacks that run at the caller's commit belong to the caller. Rule changes through NetBox's generic views and API belong to NetBox, as for every NetBox model. A restore that fails closes the raw DB-API connection and then Django's connection, and raises from the original error, whatever the transaction state at entry. A partial setup restores what it changed. Setting the timeout before either transaction opens was rejected because a trigger plan in a NetBox script starts while default is in the script's transaction. Refusing a scope that starts inside a transaction was rejected because it refuses every script in a branch. Discarding a connection only when the scope started in autocommit was rejected because a session with the changed setting can then return to the pool.

    The plugin's on_commit helper is a join of the two commits. At the call, it registers one acknowledgement on each connection with Django's own on_commit, which tags each acknowledgement with the current savepoints of that connection. The callback runs once, when both acknowledgements have fired. A rollback on either connection, of the transaction or of a savepoint around the call, drops that acknowledgement, so the callback does not run. The branch acknowledgement queues after NetBox's channel cascade, which the parent save registered earlier on the branch connection, so the channel reconciliation always runs after that cascade. On main there is one registration, as before. The trigger deferral does not use this helper. A registration on the branch connection alone was rejected because the callback then runs inside the open transaction of default, and a failed reconciliation rolls back the ChangeDiff rows of a branch family that already committed. A registration on default alone was rejected because it ran before NetBox's cascade when a caller held only the branch transaction. A registration on default that is forwarded from the branch commit was rejected because it loses a rollback of default that occurs before the branch commit.

    The internal commit marker of the plugin's transaction block stays on the branch connection. It records the branch commit before a later callback or the default commit can fail.

    The rename triggers do nothing during a netbox-branching merge, revert or sync. The plugin wraps Branch.merge, Branch.revert and Branch.sync once. Each wrapper sets a ContextVar and resets its token in a finally, so the skip ends on every exit, also on a failure or an early return. While the skip is set, the receivers read no previous state. This is the one patch of a class of another plugin, so the version check limits it to one release line and a contract test checks it. Setting the skip from netbox-branching's pre_ signals and clearing it from its post_ signals was rejected because netbox-branching does not send the post_ signals on the "no changes" return or on a failure. A reset from the branch status was rejected because it couples the plugin to netbox-branching's status values and adds one query on default for each trigger. Relying on an idempotent reapply was rejected because a rename after the merge commit runs outside event tracking and has no ObjectChange, and a rename during a sync lands in the branch with no ObjectChange, so a merge never carries it.

    The operator accepted one limit of the replay: when a merge, revert or sync replays a parent rename, NetBox's channel cascade runs again at the commit. It can then rename a channel child that the plugin kept at its old name because its configured target was taken. The plugin does not change the cascade; the documentation describes it and a test pins it.

    A job runs in the branch it was enqueued from. At enqueue, the plugin stores the schema id of the active branch and the write alias, both derived on the server. The runner puts netbox-branching's branch cookie on its synthetic request, enters NetBox's request processors strictly, and opens the write scope with the expected alias before it reads the rule. When the branch is not ready, the cookie gives no branch, the router gives default, and the job fails with an error that names both aliases. Copying the enqueuing request was rejected because it stores the session cookie in Redis. The header was rejected because netbox-branching reads it only on an API path. The query parameter was rejected because it writes flash messages. A job enqueued before the upgrade fails. There is no compatibility path, so the upgrade notes tell operators to let pending plugin jobs finish before the upgrade.

    NetBox's background REST requests (AsyncAPIJob) drop the branch identity and run on main. The REST endpoints of the rule model refuse a background request while a branch is active, with an error before any write.

    The rule cache adds the read alias to its snapshot keys and memo keys. A pinned cache checks its alias before its fast return. A cached instance must come from the alias that it serves.

    The plugin supports netbox-branching 1.2.x on NetBox 4.7. When netbox-branching is installed, startup fails with an ImproperlyConfigured error for any other version. Without netbox-branching, the plugin supports NetBox 4.3 to 4.7 with no change in behaviour. A NetBox version check was rejected because netbox-branching 1.2 already requires NetBox 4.7. Support for netbox-branching 1.1.x on NetBox 4.4.1 to 4.6 was rejected because the operator chose 1.2.x only. A warning for a later release was rejected in favour of a refusal, until the operator decides otherwise.

    These limits are accepted and documented. Nested Django atomic blocks give no atomicity across sessions: a failure of default after the branch commit, or a failure in a callback on the branch connection, leaves branch rows and ObjectChanges without ChangeDiff rows. A merge still replays them, but the branch diff view does not show them. NetBox ignores a failed branch activation in its request processors, and the core writes of that request share the problem. AsyncAPIJob drops the branch for NetBox's other endpoints, including DCIM saves that fire the rename triggers. A session SET does not survive connection pooling in transaction mode, so that pooling mode is not supported.
