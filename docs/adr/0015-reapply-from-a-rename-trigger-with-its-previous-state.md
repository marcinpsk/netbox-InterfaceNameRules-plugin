# Reapply from a rename trigger with its previous state

A rename trigger compares the previous state with the saved row, and reapplies the rules after commit. Five decisions shape it.

A save fails when its previous state cannot be read. The receivers used to catch the error and store no previous state, and the module path then read that as "no change" and dropped the reapply; the device path read it as a change. NetBox runs every edit view, bulk view and REST write inside a transaction, and PostgreSQL refuses every later statement in a transaction once one fails, so the save failed anyway and the catch only hid the cause. Reading an unknown state as "changed" was rejected because it still hides the error and does work nobody asked for.

The rename triggers of one transaction cause one reapply plan. The plan runs once, and it reapplies each module and each device at most once. It reapplies the modules of its module triggers first, and then each device. A device reapply also reapplies every module of its device, except each module that the plan already reapplied, or failed to reapply, for a module trigger: that reapply reads the device after commit too, so it is the one reapply of the module, and a failure is reported once. It compares the earliest previous state of the transaction with the committed row, so a change that the same transaction undoes reapplies nothing. The names still match the committed row, because nothing renamed them in between. Reapplying once per trigger was rejected because each reapply after the first repeats the work against the same committed rows. Each trigger is a committed callback of its own too. Django drops the callback of a trigger whose savepoint rolls back, so the plan acts only on the triggers that committed. Each trigger also appends a runner of the plan without a savepoint tag, so only a rollback of the whole transaction drops a runner. Only the newest runner runs the plan, and it comes after every trigger of the transaction. When every trigger of a plan rolled back, its runner finds no trigger to reapply. Moving one plan callback behind each new trigger was rejected, because it shifts the callbacks of other code, and a test capture that starts after a pending plan then loses a callback. Django clears run_on_commit before it runs the callbacks, so a runner cannot look for later runners there, and the plan records its newest runner instead. One reapply per module or device, which met a later trigger through a reapply that took its place, was replaced: a naming covers a whole subtree, so two of those reapplies could both act on one module, and each fix of that closed one order of the callbacks only. A module reapplies as after a type change when its type changed: only its new type's names at its new position are recognised, so a name from the old bay keeps its name and is reported. Recognising the module from the naming too was rejected, because a type change must rename every interface for a rule without channels that does not read `{base}`, and a claim over names from two module types is out of scope. Otherwise a module reapplies from its earliest naming when it moved, when its bay's naming values changed, when a module whose naming read it moved or had its bay changed, or when a module whose naming read it changed type and the module now selects another rule; and as an install when it was installed in the transaction. Each module takes the first naming read for it in the transaction, whichever trigger read it, so an edit of an outer bay and of a bay nested below it, in either order and also when the outer edit is undone, rename the nested module from the state before the first edit. The naming values of a bay are the stored position and the position that the variables read. A module installed in the transaction has no names from a rule yet, so its naming names no rule, and its raw template names are recognised as after a move without a rule before it. This is also how an install and then a move or a bay edit build a flat breakout family: the flat breakout guard that the next paragraph describes applies only to a rule that named the interfaces. The outcomes of a module go to the journal entry of the outermost module whose moved, edited or retyped naming read it, and to the module itself when there is none. So a nested module with a trigger of its own, inside a moved or retyped card or an edited bay, is reported on the card or on the module in the bay, with the rest of that subtree. This is one entry for the whole subtree, as a bay edit reports. A module that another module's naming read before it moved out reports on that outer module too.

A reapply recognises the interfaces the plugin renamed earlier by rebuilding their earlier names from the previous state: the old module bay and its position and name, the old device and the old virtual-chassis position. The earlier names come from the rule that the previous state selects, and the new names from the rule that the saved row selects, because the device type, the platform and the parent module type decide which rule wins. A move reads the previous state of the moved module and of every module nested in it before the save, because in the same save NetBox 4.7 can re-resolve the position and name of each bay that the moved module holds. A bay edit reads it for the module in the bay and for every module nested in it, because the variables of the nested modules read the bay's position too. A bay edit is a trigger only when it changes the bay's stored position, or the position that the variables read, which for a bay whose position is a template token comes from the trailing digits of its name. Reapplying after every name change was rejected, because the claim reports every unclaimed interface and every flat family, so an unrelated rename would write journal entries. NetBox 4.7 sends the post_save of each nested bay by hand during a move, with no pre_save, and that is not a bay trigger: the move reads the naming of that subtree itself. A type change reads the previous state of the module and of every module nested in it before the save. A rule can be scoped to a parent module type, so a module nested in the changed module can select another rule after the save. The type change reads that state only when an enabled rule has the old or the new type as its parent module type. Without such a rule, every nested module selects the same rule before and after. This check is one EXISTS query on each type change. It does not use the rule cache: a cache that is not current loads every rule, and that load would then run during the save. The check reads the rules in force at the module save, so a rule enabled later in the same transaction does not cause a nested naming read. After commit, a nested module reapplies from that naming only when it now selects another rule. A nested module whose rule does not change keeps its names and is not reported. Reapplying every nested module was rejected. The claim from a naming reports every interface that no template claims, so a type change would write journal entries for modules that it does not affect. Reading the naming on every type change was rejected, because it adds a subtree read to each type change that no rule scope needs. The read of a type change is the earliest naming of the transaction. So a later move or bay edit of that module in the same transaction recognises the nested modules from the state before the type change. NetBox 4.7 renames a moved module's interfaces only while they carry their raw template name, and NetBox renames no interface after a bay edit, so after a move or a bay edit an interface the plugin renamed carries a name built from a position that no longer exists. After a move, a bay edit or a type change of the parent module every rule claims its names through these forms, not only a rule that reads `{base}`, so an interface that no single template claims keeps its name and is reported. A move, a bay edit or a type change of the parent module does not rename a flat breakout family. When the rule that the previous state selects for a module is a flat breakout rule, the reapply renames nothing on that module and reports each of its interfaces; the other modules of the subtree reapply as usual. NetBox stores no link from an interface to its template or to its family, so a flat family can be recognised only by its names, and five review rounds each found a new case where name-based recognition renamed an interface wrongly or renamed part of a family. Recognising families by name was rejected for that reason. A plugin-side record of family membership was rejected here because it is a larger design, and it belongs in a ticket of its own. A move into a flat rule's scope still builds the family on a claimed interface as an install does. A move renames nothing on a module while any of its top-level interfaces, neither a channel nor a subinterface, is unclaimed, and reports every interface: an unclaimed one can belong to a family, and renaming its claimed neighbours split a family in the sixth review round. A module type without interface templates claims nothing after a move or a bay edit. A module whose interfaces are on another device than the module renames nothing, and each interface is reported. NetBox before 4.7 writes only the module row of a move, so after a move to another device the interfaces stay on the old device, and names built for the new device would be wrong there. For the same reason, a module whose bay has a parent bay that does not hold the module owning the bay renames nothing, and each interface is reported: the module type installed in the parent bay helps select the rule, and after the move that parent bay is empty. The claim replaces the admission guard of an install on this path. Matching any bay position, as the `{vc_position}` claim does, was rejected because a wider match makes more rows ambiguous, and an ambiguous row is left alone. Not recognising them was rejected because nothing else can: Apply Rules has no previous state, so a missed move leaves the name wrong until an operator fixes it by hand. Names left wrong by moves or bay edits made before this change stay wrong for the same reason, and the documentation says so. The names that a module's interfaces carry at commit come from one naming point of the transaction. Before the transaction they carry the names of the earliest naming read for the module, which the plan resolves at the virtual-chassis position that its device had before its first trigger of the transaction, or with no `{vc_position}` when the device then had no chassis or no position; nothing renamed the interfaces between that trigger and the read. An install names the raw names with NetBox's resolve_name. On NetBox 4.7 each move that carries the module, also as a nested module, names them with the resolver of NetBox's move planner, which resolves a `{vc_position}` token also when only a bay position brings it in. A naming point names the bay chain that the next naming read of the module holds, or the committed bay chain after the last read, at the position that the device of that bay chain had at that point. Every move and every change of what a bay's names are built from reads a naming, so nothing changes the bay chain between a point and the next read. A read before the install of a module was for a module deleted since, and counts for no point. The plan knows every point after commit, and needs no read for it: a move trigger records that it moved the module, the triggers keep their order, and the plan has the place of every device trigger; a device trigger reads no naming. The claim recognises the raw names of every point, each from the resolver that NetBox used there, as well as the current names and the forms of the earliest naming. A rule gives names only before the transaction, because the plugin renames only after commit and a move renames only raw names, so the forms of the earliest naming cover the names of a rule. A name from a point is recognised only when one template alone claims it, so a name that two templates give at different points is refused. A device reapply recognises the names of each of its modules at the position of the device before its first trigger. NetBox is the one source of each name: a resolved template keeps the template and the module it was resolved against, and resolves the name through NetBox's own resolver against an unsaved copy of that module whose device copy has the position of the point, or no virtual chassis. The copies share the bay chain that the read loaded, so the name comes from the bay at that point, no query runs, and nothing changes on the module or its device. Rebuilding the name from the template text around its tokens was rejected: NetBox resolves `{module}` before the position, also inside a token's fallback and in a bay position that brings its own token, and each rebuild missed one of those orders. Recognising only the last naming point was rejected, because NetBox keeps a raw name at a move when the device's position changed since the name was given, so the name comes from an earlier point. Relying on the any-position matcher for the names of a point was rejected: it has no matcher for a template name with adjacent `{vc_position}` tokens, for a fallback that holds `{module}`, or for a token that a bay position brings in. Building a naming at an install was rejected, because a naming makes the reapply claim as after a move: it adds no stand-in, so a module type without templates recognised nothing, and it reports a hand-added interface and renames nothing on the module. A device reapply leaves out each module that the plan reapplied, or failed to reapply, for a module trigger, so each outcome is reported once, on the journal entry of the module reapply. A module that a module trigger reaches but that needs no reapply of its own, such as a module that a move out and back returned to its bay, is reapplied by its device. Keeping the device reapply as a fallback for the modules that the module reapply left unclaimed was rejected, because it brings back the double reapply and its contradictory reports. Leaving those modules out of the device reapply without the naming points was rejected: after a position change and then a bay edit, a rule with `{vc_position}` in arithmetic could not recognise the old names, so the module kept them and was reported. Reading the naming of every module of a device on each virtual-chassis change was rejected, because it adds work to every such save, and the plan needs only the position of the device before its first trigger. The previous state holds the module type, bay and device, the naming values of a bay, the naming of the subtree of a moved module, of the module in an edited bay or of a module whose type changed while a rule is scoped to the old or the new type as a parent module type, and the virtual-chassis values.

A reapply that fails, or that leaves an interface unrenamed although a rule matched it, writes one journal entry on the module or device, as well as the log line. The entry keeps the interface outcomes found before a failure, and adds one line for the failure, which names no interface. A failure while the plan decides how to reapply a module, such as a failed read of the rules, is a failure of that module, and the other modules still reapply. A reapply that cannot read the committed module or device writes only the log line, because no row is available to hold the entry. The save has committed by then and cannot be undone, and raising would show an error page for a save that succeeded. A log line alone was rejected because operators do not read the server log. A background job was rejected for now because it makes the rename no longer immediate.

A module install outside a transaction renames nothing, and this is accepted. NetBox sends post_save for a new module before it creates the module's interfaces, and with no transaction open the after-commit reapply runs at once and finds no interfaces. The web UI, the REST API and bulk import always open a transaction, so only scripts and shell sessions are affected, and Apply Rules repairs them. An interface-side trigger was rejected for now because it adds a trigger on every interface save to fix a path that NetBox itself does not use.
