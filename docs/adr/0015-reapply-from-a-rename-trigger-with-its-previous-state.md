# Reapply from a rename trigger with its previous state

A rename trigger compares the previous state with the saved row, and reapplies the rules after commit. Five decisions shape it.

A save fails when its previous state cannot be read. The receivers used to catch the error and store no previous state, and the module path then read that as "no change" and dropped the reapply; the device path read it as a change. NetBox runs every edit view, bulk view and REST write inside a transaction, and PostgreSQL refuses every later statement in a transaction once one fails, so the save failed anyway and the catch only hid the cause. Reading an unknown state as "changed" was rejected because it still hides the error and does work nobody asked for.

Several rename triggers for one module or device in one transaction cause one reapply. It compares the earliest previous state of the transaction with the committed row, so a change that the same transaction undoes reapplies nothing. The names still match the committed row, because nothing renamed them in between. Reapplying once per trigger was rejected because each reapply after the first repeats the work against the same committed rows. When one transaction changes a module's type and moves it, the move's naming reaches the pending reapply through a reapply that takes its place ahead of it in the same savepoint, so a savepoint that rolls back leaves the pending reapply as it was. The module itself is reapplied as after a type change: only its new type's names at its new position are recognised, so a name from the old bay keeps its name and is reported. The modules nested in it are recognised from that naming. Recognising the module from the naming too was rejected, because a type change must rename every interface for a rule that does not read `{base}`, and a claim over names from two module types is out of scope. A bay edit schedules the reapply of the module in the bay, not a reapply of its own, so a bay edit, a type change and a move of one module in one transaction share one reapply, and it keeps the earliest naming. That naming also holds the naming values of the module's bay, which are the stored position and the position that the variables read, and the reapply compares them with the committed bay: several edits of one bay reapply once, an edit that the transaction undoes reapplies nothing, and a module that moves out and back into a bay edited in the same transaction is renamed. A reapply of its own for the bay was rejected, because it needs a second dedup path, and a move of the module after the edit could not keep the naming from before the edit. The reapplies of one transaction also share what named each module: when a save reads the naming of a module that a pending reapply read earlier, the new reapply takes the earlier entry. So an edit of an outer bay and of a bay nested below it, in either order and also when the outer edit is undone, rename the nested module from the state before the first edit, and no reapply reports it as unclaimed. A module whose install reapply is pending has no names from a rule yet, so its entry names no rule, and its raw template names are recognised as after a move without a rule before it. This is also how an install and then a move or a bay edit build a flat breakout family: the flat breakout guard that the next paragraph describes applies only to a rule that named the interfaces. An entry from a savepoint that rolls back leaves with its reapply, because Django drops that callback.

A reapply recognises the interfaces the plugin renamed earlier by rebuilding their earlier names from the previous state: the old module bay and its position and name, the old device and the old virtual-chassis position. The earlier names come from the rule that the previous state selects, and the new names from the rule that the saved row selects, because the device type, the platform and the parent module type decide which rule wins. A move reads the previous state of the moved module and of every module nested in it before the save, because in the same save NetBox 4.7 can re-resolve the position and name of each bay that the moved module holds. A bay edit reads it for the module in the bay and for every module nested in it, because the variables of the nested modules read the bay's position too. A bay edit is a trigger only when it changes the bay's stored position, or the position that the variables read, which for a bay whose position is a template token comes from the trailing digits of its name. Reapplying after every name change was rejected, because the claim reports every unclaimed interface and every flat family, so an unrelated rename would write journal entries. NetBox 4.7 sends the post_save of each nested bay by hand during a move, with no pre_save, and that is not a bay trigger: the move reads the naming of that subtree itself. NetBox 4.7 renames a moved module's interfaces only while they carry their raw template name, and NetBox renames no interface after a bay edit, so after a move or a bay edit an interface the plugin renamed carries a name built from a position that no longer exists. After a move or a bay edit every rule claims its names through these forms, not only a rule that reads `{base}`, so an interface that no single template claims keeps its name and is reported. A move or a bay edit does not rename a flat breakout family. When the rule that the previous state selects for a module is a flat breakout rule, the reapply renames nothing on that module and reports each of its interfaces; the other modules of the subtree reapply as usual. NetBox stores no link from an interface to its template or to its family, so a flat family can be recognised only by its names, and five review rounds each found a new case where name-based recognition renamed an interface wrongly or renamed part of a family. Recognising families by name was rejected for that reason. A plugin-side record of family membership was rejected here because it is a larger design, and it belongs in a ticket of its own. A move into a flat rule's scope still builds the family on a claimed interface as an install does. A move renames nothing on a module while any of its top-level interfaces, neither a channel nor a subinterface, is unclaimed, and reports every interface: an unclaimed one can belong to a family, and renaming its claimed neighbours split a family in the sixth review round. A module type without interface templates claims nothing after a move or a bay edit. A module whose interfaces are on another device than the module renames nothing, and each interface is reported. NetBox before 4.7 writes only the module row of a move, so after a move to another device the interfaces stay on the old device, and names built for the new device would be wrong there. For the same reason, a module whose bay has a parent bay that does not hold the module owning the bay renames nothing, and each interface is reported: the module type installed in the parent bay helps select the rule, and after the move that parent bay is empty. The claim replaces the admission guard of an install on this path. Matching any bay position, as the `{vc_position}` claim does, was rejected because a wider match makes more rows ambiguous, and an ambiguous row is left alone. Not recognising them was rejected because nothing else can: Apply Rules has no previous state, so a missed move leaves the name wrong until an operator fixes it by hand. Names left wrong by moves or bay edits made before this change stay wrong for the same reason, and the documentation says so. A device reapply and a module reapply do not share a previous state: when one transaction changes a device's virtual-chassis position and then moves a module out of the device, names the move cannot rebuild keep their names and are reported. Only scripts and shell sessions save two models in one transaction, and a shared naming context was rejected because it adds state across triggers for that case, which already fails safe. The previous state holds the module type, bay and device, the naming values of a bay, the naming of the subtree of a moved module or of the module in an edited bay, and the virtual-chassis values.

A reapply that fails, or that leaves an interface unrenamed although a rule matched it, writes one journal entry on the module or device, as well as the log line. The entry keeps the interface outcomes found before a failure, and adds one line for the failure, which names no interface. A reapply that cannot read the committed module or device writes only the log line, because no row is available to hold the entry. The save has committed by then and cannot be undone, and raising would show an error page for a save that succeeded. A log line alone was rejected because operators do not read the server log. A background job was rejected for now because it makes the rename no longer immediate.

A module install outside a transaction renames nothing, and this is accepted. NetBox sends post_save for a new module before it creates the module's interfaces, and with no transaction open the after-commit reapply runs at once and finds no interfaces. The web UI, the REST API and bulk import always open a transaction, so only scripts and shell sessions are affected, and Apply Rules repairs them. An interface-side trigger was rejected for now because it adds a trigger on every interface save to fix a path that NetBox itself does not use.
