# Reapply from a rename trigger with its previous state

A rename trigger compares the previous state with the saved row, and reapplies the rules after commit. Five decisions shape it.

A save fails when its previous state cannot be read. The receivers used to catch the error and store no previous state, and the module path then read that as "no change" and dropped the reapply; the device path read it as a change. NetBox runs every edit view, bulk view and REST write inside a transaction, and PostgreSQL refuses every later statement in a transaction once one fails, so the save failed anyway and the catch only hid the cause. Reading an unknown state as "changed" was rejected because it still hides the error and does work nobody asked for.

Several rename triggers for one module or device in one transaction cause one reapply. It compares the earliest previous state of the transaction with the committed row, so a change that the same transaction undoes reapplies nothing. The names still match the committed row, because nothing renamed them in between. Reapplying once per trigger was rejected because each reapply after the first repeats the work against the same committed rows. When one transaction changes a module's type and moves it, the move's naming reaches the pending reapply through a reapply that takes its place ahead of it in the same savepoint, so a savepoint that rolls back leaves the pending reapply as it was. The module itself is reapplied as after a type change: only its new type's names at its new position are recognised, so a name from the old bay keeps its name and is reported. The modules nested in it are recognised from that naming. Recognising the module from the naming too was rejected, because a type change must rename every interface for a rule that does not read `{base}`, and a claim over names from two module types is out of scope.

A reapply recognises the interfaces the plugin renamed earlier by rebuilding their earlier names from the previous state: the old module bay, the old device and the old virtual-chassis position. The earlier names come from the rule that the previous state selects, and the new names from the rule that the saved row selects, because the device type, the platform and the parent module type decide which rule wins. A move reads the previous state of the moved module and of every module nested in it before the save, because in the same save NetBox 4.7 can re-resolve the position and name of each bay that the moved module holds. NetBox 4.7 renames a moved module's interfaces only while they carry their raw template name, so after a move or a bay-position edit an interface the plugin renamed carries a name built from a position that no longer exists. After a move every rule claims its names through these forms, not only a rule that reads `{base}`, so an interface that no single template claims keeps its name and is reported. A flat family takes part in that one claim as one group of all its member names. It is renamed only when its template claims nothing else and no other template claims any of its members, so a template that names two families, or a family and an interface, claims none of them, and neither does a template whose family shares a member with another template's claim. Checking one member of a family was rejected because another template can claim a later member. The move path gathers every form and every complete family from every base first and resolves them in one pass: resolving the historical families in an earlier stage dropped them before the previous family was added, so a template that named three families claimed one. Within one template, a name or a family inside another of its groups is the same claim, so a raw name inside the template's own family does not refuse it. Only the group a template's claim won becomes a plan: a family absorbed into a larger one is no plan of its own, so a family with more channels than the new rule keeps every name instead of half of it being renamed. Planning refuses an interface that two plans hold before any plan runs. A module type without interface templates claims nothing after a move. The claim replaces the admission guard of an install on this path. Matching any bay position, as the `{vc_position}` claim does, was rejected because a wider match makes more rows ambiguous, and an ambiguous row is left alone. Not recognising them was rejected because nothing else can: Apply Rules has no previous state, so a missed move leaves the name wrong until an operator fixes it by hand. Names left wrong by moves made before this change stay wrong for the same reason, and the documentation says so. Reapplies of different objects do not share a previous state: when one transaction changes a device or a bay and then moves a module out of it, names the move cannot rebuild keep their names and are reported. Only scripts and shell sessions save two models in one transaction, and a shared naming context was rejected because it adds state across triggers for that case, which already fails safe. The bay-edit trigger (#120) is not implemented yet; today the previous state holds the module type, bay and device, the naming of a moved module's subtree, and the virtual-chassis values.

A reapply that fails, or that leaves an interface unrenamed although a rule matched it, writes one journal entry on the module or device, as well as the log line. The entry keeps the interface outcomes found before a failure, and adds one line for the failure, which names no interface. A reapply that cannot read the committed module or device writes only the log line, because no row is available to hold the entry. The save has committed by then and cannot be undone, and raising would show an error page for a save that succeeded. A log line alone was rejected because operators do not read the server log. A background job was rejected for now because it makes the rename no longer immediate.

A module install outside a transaction renames nothing, and this is accepted. NetBox sends post_save for a new module before it creates the module's interfaces, and with no transaction open the after-commit reapply runs at once and finds no interfaces. The web UI, the REST API and bulk import always open a transaction, so only scripts and shell sessions are affected, and Apply Rules repairs them. An interface-side trigger was rejected for now because it adds a trigger on every interface save to fix a path that NetBox itself does not use.
