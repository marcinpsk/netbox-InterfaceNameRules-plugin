# Take over existing channel rows when building a channelized family

When the plugin builds a channelized family on a plain port, a row that already has one of the planned channel names is taken over instead of counted as a collision, when it qualifies. Other tooling often creates the channel interfaces of a breakout optic on the device before the optic is modelled, with LAG membership, addresses and VLANs on them. Refusing the family because those rows exist left the device with flat rows and a parent that has no channels. This ADR revises ADR 0013 for channelized creation only: a channelized family can take a row by its name. A flat family still keeps only the rows the claim gives it, and a channelized family that the module already models still renames as before.

A row with a planned channel name qualifies when it is not on another module (its module is empty or is the family's module), has no parent and no channel ID, and is not a channelized parent. A row with a cable does not qualify. NetBox 4.7 refuses a channel ID on an interface that has a cable termination, because a channel takes its cable from its parent. The plugin never edits or deletes a cable, so the operator must remove the cable first. One function, `channel_holder_refusal`, states this rule. Planning, the preview and execution all call it, so they cannot disagree about which rows qualify. The parent name rule does not change: a row other than the base with the parent's target name refuses the family.

To take over a row, the plugin keeps its primary key and name, and sets its module to the family's module, its parent to the family parent, its channel ID to the planned one and its type to `channel`. These are the values of a channel row that the plugin creates or that a conversion rewrites. Everything else on the row stays: LAG membership, addresses, VLANs, description, enabled state, tags and custom field values. NetBox's `full_clean()` validates each row that the family takes over, and a rejection names the row. A planned channel that has no row is created as before.

The decision is all or nothing (ADR 0001). When one row with a planned name does not qualify, or NetBox rejects one row, the family is refused and no row changes. The reason names the row and says why it does not qualify. The refusal outcome reports the base and every row that the family would take over, once each, with that reason. A taken-over row is a member of the family outcome with status `changed` and the name it already had, so the Apply view counts it.

A structural plan carries a snapshot of each row with a planned channel name. Execution runs in the family's own transaction (ADR 0005). It locks the base and those rows in primary-key order and compares them with their snapshots (ADR 0002). A row that changed, that is gone, or that took a planned channel name after planning makes the plan stale. Discovering the rows only at execution was rejected, because then a row could change between the decision and the write with nothing to compare against.

The preview asks the executor's question with the same function, so it offers a family whose rows all qualify and offers no family that the apply refuses. It records the reason that the apply gives. Prediction has no rows (ADR 0008), so it predicts the family whether or not a row with a channel name qualifies.

A row that the family takes over is not a flat sibling. The module-wide check for an installed flat family (ADR 0010) counts plain rows beyond the module type's templates, so it leaves out the rows with a planned channel name. A flat apply gives the first row of a flat family a channel name, so this does not apply when the base itself has one of the planned channel names: then the rows are still that flat family, and only an operator-confirmed conversion changes them. For the same reason, under a channelized rule the claim (ADR 0013) does not read rows with the channel names as a flat family of a template while the module still has that template's raw name. A flat apply renames the port, so rows beside a raw-named port came from other tooling. Without this, the claim found the port and those rows ambiguous and refused both. A row that the family takes over has no plan of its own, so it is reported once.
